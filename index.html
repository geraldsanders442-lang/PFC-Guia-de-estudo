01

Visão geral

O que o sistema faz antes de falar de ferramentas.

O Escape.py é um jogo web educacional no formato Escape Room. A equipe explora uma sala, encontra pistas e resolve enigmas escrevendo funções em Python. A meta pedagógica é praticar lógica, leitura de problemas, testes e colaboração.

Experiência do jogador

Explorar → descobrir → programar

O jogador entra na conta, participa de um grupo, navega por cenários com objetos clicáveis, lê pistas no caderno compartilhado e abre um editor de código para resolver os mecanismos.

Uma divisão importante

Python é o conteúdo, JavaScript é a aplicação

O site e sua lógica são escritos principalmente em JavaScript. O código Python digitado pelos estudantes é executado dentro do navegador pelo Pyodide; não é o servidor Node que executa esse Python.

Partida em cinco passos

1 · IdentidadeCadastro, verificação de e-mail e perfil.
2 · EquipeGrupos, participantes, convites e chat.
3 · PreparaçãoO proprietário escolhe a dificuldade e cria a configuração.
4 · DesafioPistas liberam enigmas; Python é testado localmente no browser.
5 · ResultadoO back-end registra progresso, tempo e pontuação.

02

Como as partes conversam

Uma aplicação web em três camadas, com um canal adicional de notificações em tempo real.

1 · NavegadorHTML, CSS e módulos JavaScript. Mostra telas e envia ações pela API.
2 · API RESTNode.js + Express autenticam, validam e aplicam regras de negócio.
3 · BancoMongoDB Atlas guarda contas, grupos, convites, mensagens e partidas.
Canal SSEO servidor avisa que algo mudou; o front faz novo GET para buscar o estado atual.

O navegador não se conecta diretamente ao MongoDB. Ele chama endpoints como GET /api/groups ou POST /api/games/{id}/start. O servidor verifica quem está chamando e se aquela operação é permitida, então consulta ou atualiza a base e devolve JSON.

Fluxo conceitual · não é uma chamada única de código
Navegador → HTTPS + JSON → API Express → MongoDB Atlas
Navegador ← resposta JSON ← API Express ← consulta/gravação
Navegador ← aviso SSE ("partida mudou") ← API Express
Navegador → GET novamente → API Express → estado mais recente

SSE não transmite, por si só, o estado completo do jogo. O evento informa qual canal mudou; em seguida, o cliente consulta a API. Esse desenho evita usar a notificação como fonte final dos dados.

HTML5 e acessibilidade

HTML define a estrutura e o significado do conteúdo; não é a linguagem que processa as regras do jogo.

O HTML descreve elementos como cabeçalhos, formulários, botões, links, áreas principais e painéis. Elementos semânticos ajudam leitores de tela, navegação por teclado, mecanismos de busca e manutenção do código.

É mais claro para pessoas e tecnologia assistiva: <button> é acionável, <nav> é navegação, <main> é conteúdo principal. É melhor que transformar qualquer <div> em controle clicável.

CSS3 e responsividade

CSS controla apresentação, posicionamento e adaptação a diferentes telas.

No projeto, há estilos globais em css/style.css e regras específicas da sala em css/sala.css. A tela do jogo usa grid para separar área de exploração e painel lateral; uma media query transforma o arranjo em uma coluna em telas menores.

Padrão que existe em css/sala.css
.sala-layout {
  display: grid;
  grid-template-columns: minmax(0, 1fr) 340px;
  gap: 18px;
}

@media (max-width: 1100px) {
  .sala-layout { grid-template-columns: 1fr; }
}

minmax(0, 1fr) permite que a área principal encolha sem estourar a grade. A media query aplica outro layout quando a largura disponível cai. Unidades relativas, conteúdo fluido e áreas de toque razoáveis são importantes para telefone. A folha da sala também preserva um palco em proporção 16 / 9.

Como explicar a separação

HTML organiza o que existe; CSS decide como aparece; JavaScript muda os dados e reage a ações. Separar as responsabilidades torna mais fácil ajustar o visual sem reescrever a regra do jogo.

06

JavaScript no projeto

JavaScript liga as interações da interface, os serviços web e a lógica executada no navegador.

O código da interface está organizado em classes e módulos ES. JavaScript usa funções, objetos, classes, arrays, mapas, eventos e Promises. Operações de rede e algumas regras são assíncronas: a palavra-chave await espera uma Promise sem congelar toda a interface.

Padrão usado no fluxo da partida · versão didática
async function iniciarPartida() {
  try {
    await servicoPartida.iniciar(idGrupo);
    // A API confirmou a ação; o estado atualizado chega pela observação.
  } catch (erro) {
    notificador.falha(erro, "Não foi possível iniciar.");
  }
}

async faz a função retornar uma Promise. await pausa aquela função até a resposta. try/catch apresenta falhas de rede ou regras negadas de modo controlado.

Como o site atualiza a tela?

Eventos DOM, como click e change, chamam métodos; esses métodos consultam serviços e alteram os elementos DOM. Para dados externos, não se deve confiar no que o cliente mostra: a API valida a operação de novo.

ES Modules e organização

Módulos permitem dividir o programa em arquivos com responsabilidades e dependências explícitas.

As páginas carregam js/main.js como type="module". O arquivo importa classes com import, expõe itens com export e usa importação dinâmica da página correta. O package.json do back-end define "type":"module", portanto usa a mesma sintaxe ES Modules no Node.js.

Trecho de js/main.js
const classe = Aplicacao.PAGINAS[document.body.dataset.pagina];
if (!classe) return;
const modulo = await import(`./paginas/${classe}.js`);
await new modulo[classe]().iniciar();

Essa importação tardia carrega a classe necessária para a página atual, em vez de inicializar toda tela possível em todas as páginas. Os nomes de pastas refletem as responsabilidades: paginas, componentes, servicos, modelos e nucleo.

HTTP, JSON e API REST

Uma API é o contrato que permite ao front solicitar operações ao back-end.

O projeto usa HTTP com recursos organizados em caminhos e métodos: GET consulta, POST cria ou executa ações, PATCH altera parcialmente, PUT substitui/atualiza um recurso e DELETE remove. JSON é o formato dos corpos e respostas. As URLs começam por /api.

ExemploO que significaResposta comum
POST /api/auth/loginEnviar credenciais para autenticarJSON com token e dados do usuário
GET /api/groupsBuscar grupos do usuário autenticadoJSON com lista de grupos
POST /api/games/{id}/startPedir para começar uma partida204 se aceito
PATCH /api/users/meAtualizar campos permitidos do próprio perfilJSON atualizado

Em js/nucleo/Api.js, a camada cliente usa fetch, serializa o corpo com JSON.stringify, adiciona Authorization: Bearer … quando existe sessão e converte erros HTTP em ErroApi.

Requisição simplificada
fetch("/api/groups", {
  method: "POST",
  headers: {
    "Content-Type": "application/json",
    "Authorization": `Bearer ${token}`
  },
  body: JSON.stringify({ name: "Equipe Corvos" })
});

Front-end: páginas, componentes e serviços

O front-end estático apresenta as telas e solicita mudanças ao servidor; não hospeda a base de dados.

Páginas

Componentes

js/componentes/ desenha partes reutilizáveis: mesa, chat, caderno, mapa, painéis de enigma e resultado.

Serviços

Lógica do jogo e geração procedural

Uma configuração derivada de semente define a sequência de pistas, enigmas e dependências.

GeradorProcedural usa uma semente e a dificuldade para selecionar objetos, modelos de enigma e relações entre etapas. A mesma semente torna possível reproduzir a mesma sequência aleatória derivada, desde que a versão do gerador e as entradas sejam iguais. O gerador valida a configuração e simula a progressão para verificar se o final é alcançável.

Esquema simplificado do fluxo
const semente = Aleatorio.novaSemente();
const { config } = GeradorProcedural.gerar({ sala, dificuldade, semente });
await servico.criar(idGrupo, { uid, dificuldade, semente, config });

EstadoPartida modela estados como WAITING, PLAYING, COMPLETED, FAILED e EXPIRED. As transições permitidas são explícitas. O servidor define o horário real de início e expiração; o cronômetro do navegador apenas exibe o tempo sincronizado.

Regra importante: a validação pedagógica do código Python acontece no navegador; o servidor registra o fato de que uma pista/enigma foi concluído e confere pré-condições, participação, estado, prazo e limites. Não diga que a API executa o código Python dos jogadores.

Hotspots

A sala é composta por renders/imagens e uma camada SVG sobreposta. Hotspots são áreas clicáveis associadas a objetos. As coordenadas são normalizadas no JSON da sala, permitindo redimensionar o palco sem depender de um tamanho fixo de imagem. O editor de sala administra essas áreas e a publicação da configuração.

Colaboração

Vários participantes podem observar o estado compartilhado. Se alguém encontra pista ou resolve um mecanismo, a API registra e emite um aviso SSE. Os demais clientes então recarregam o estado, atualizam caderno/progresso e mostram feedback.

Python, Pyodide e Web Worker

Python é executado no navegador por meio do runtime WebAssembly do Pyodide.

Pyodide disponibiliza o interpretador Python compilado para WebAssembly. ExecutorPython envia o código para um Web Worker, uma thread separada da interface. Assim, enquanto o código roda, a tela principal pode continuar responsiva. O Worker carrega a versão 0.26.4 do Pyodide e aplica testes definidos pelo enigma.

1 · EditorJogador escreve uma função Python.
2 · MensagemJavaScript manda código e identificador ao Worker.
3 · ExecuçãoPyodide interpreta e executa os testes de entrada/saída.
4 · FeedbackWorker devolve resultado; painel mostra erros, saída ou aprovação.
Interface JavaScript simplificada com Worker
const worker = new Worker("./PyodideWorker.js");
worker.postMessage({ id, codigo, nomeFuncao, testes, modo: "validar" });
worker.addEventListener("message", ({ data }) => {
  if (data.tipo === "resultado" && data.id === id) {
    mostrarResultado(data.resultado);
  }
});

Testes do enigma

O harness Python analisa/compila o texto, executa-o, localiza a função esperada e compara retorno com casos de teste. Ele diferencia erro de sintaxe, erro em execução e falha de teste. Há um limite de 6 segundos para execução; se expirar, o Worker é encerrado e descartado para interromper código travado.

Limite de segurança que vale conhecer: executar código no navegador isola a interface por Worker e permite terminar a tarefa por tempo, mas não deve ser apresentado como sandbox inviolável contra qualquer abuso. O navegador do estudante é o ambiente de execução; o back-end não valida por conta própria toda semântica do código digitado. Essa é uma decisão e uma limitação técnica a discutir com honestidade.

O aluno não envia um programa Python para executar no servidor. O servidor recebe apenas a ação de progresso e seus metadados (por exemplo, dicas/tentativas/pontuação), e aplica validações de domínio e autorização sobre o estado.

Tempo real com Server-Sent Events

SSE é um fluxo persistente unidirecional: servidor → navegador.

A rota GET /api/events mantém uma conexão HTTP aberta com tipo text/event-stream. Quando algo relevante muda, o servidor publica um pequeno evento com o nome do canal: grupo, chat, partida, convite ou presença. O navegador assina os canais usados pela página e, ao receber um aviso, busca de novo o recurso via API REST.

Por que SSE?

O jogo precisa principalmente que o servidor avise o navegador sobre atualizações. SSE é mais simples que comunicação bidirecional quando o envio de comandos continua acontecendo por HTTP normal.

Por que não WebSocket?

WebSocket é bidirecional e adequado para troca constante nos dois sentidos. Para este fluxo — enviar ações por REST e receber notificações — SSE reduz complexidade.

TempoReal.js implementa conexão, leitura do fluxo, reconexão com espera crescente, e recarga de dados após reconexão para reparar avisos perdidos. O Worker no servidor guarda conexões em memória; por isso o README avisa que o deploy precisa ser de uma instância única para esse recurso consistente.

Distinção para a banca: eventos SSE avisam “houve mudança”; REST busca “qual é o estado agora”. SSE atual é unidirecional; não é chat de WebSocket. O cliente envia mensagens por endpoints HTTP normais.

Node.js e Express

Node executa JavaScript no servidor; Express facilita construir o servidor HTTP e suas rotas.

Node.js é o runtime que executa JavaScript fora do browser. No projeto, executa a API e scripts de testes. Express 5 fornece roteamento, middlewares e integração para responder a requisições. A API abre na porta configurada (padrão local 3000) e tem endpoint de saúde /api/health.

Trecho adaptado de backend/src/app.js
const app = express();
app.use(cors({ origin: validarOrigem }));
app.use(express.json({ limit: "1mb" }));
app.use("/api/auth", rotasAutenticacao(limites));
app.use("/api/groups", rotasGrupos());
app.use("/api/games", rotasPartidas());
app.use(tratarErros);

Um middleware é uma função na cadeia de processamento: pode inspecionar a requisição, preencher contexto, bloquear acesso ou passar adiante com next(). A ordem importa: CORS/JSON/limites e rotas são instalados antes do middleware final de erro.

MongoDB Atlas

Banco de dados orientado a documentos, hospedado como serviço gerenciado.

MongoDB guarda documentos BSON com formato semelhante a JSON em coleções. O projeto usa o driver oficial mongodb em Node.js e conecta ao Atlas no arranque do servidor. Exemplos de coleções: users, groups, games, messages, invites, authTokens e auditLogs.

Conexão real simplificada · backend/src/config/banco.js
const cliente = new MongoClient(uri);
await cliente.connect();
const db = cliente.db(nomeDoBanco);
await db.command({ ping: 1 });
return { cliente, db };

Índices aceleram consultas e podem impor unicidade, por exemplo e-mail único. Índices TTL fazem o MongoDB remover documentos expirados (tokens de uso único e mensagens temporárias). Um índice não substitui validação de negócio nem autorização.

Por que manter banco só no servidor?

A API centraliza validações, regras de acesso e segredo de conexão. O navegador nunca recebe credenciais do banco. O servidor atualiza estado compartilhado e impede que cada cópia local do front escolha sozinha quem pode avançar uma partida.

17

Autenticação e segurança

Identidade responde “quem é você?”; autorização responde “o que você pode fazer?”.

bcrypt

Função de hash de senha com salt e custo computacional ajustável. O sistema guarda um hash (custo configurado como 12), nunca a senha em texto puro. A verificação compara a senha digitada ao hash.

JWT

JSON Web Token assinado pelo servidor e enviado pelo cliente como token Bearer. O projeto assina com HS256 e inclui id/versionamento de sessão e validade. Assinatura permite detectar alteração; JWT não é automaticamente criptografado.

CORS

Política de navegador que restringe quais origens podem ler respostas cross-origin. A API compara a origem com FRONTEND_URL. CORS não substitui autenticação nem é uma barreira contra chamadas fora do browser.

Rate limiting

express-rate-limit controla frequência de requisições, especialmente rotas sensíveis, para reduzir abuso e tentativas repetidas. Ele complementa, não substitui, segurança de senha.

Fluxo resumido de sessão

  1. O jogador envia e-mail e senha por HTTPS.
  2. O servidor verifica a senha com bcrypt e emite JWT de validade limitada.
  3. O navegador armazena o token no localStorage e anexa Authorization: Bearer … às chamadas.
  4. Middleware verifica assinatura/expiração, busca usuário no banco e compara versão da sessão.
  5. Middlewares específicos exigem e-mail verificado, perfil completo ou papel de administrador, conforme a rota.
Decisão e risco: o README explica que o JWT foi colocado em localStorage para suportar front e back em domínios distintos. JavaScript acessível na página também pode ler esse armazenamento, então XSS é um risco. A aplicação reduz exposição com expiração curta e inserção de conteúdo de usuário usando textContent; isso não elimina todos os riscos.

Validação no servidor

Dados vindos do cliente não são confiáveis. O servidor limita formato/tamanho, usa IDs e chaves validados e checa propriedade, associação ao grupo, status da partida, prazo e pré-requisitos. CORS não é controle de acesso. O segredo JWT e URI do Mongo devem ficar em variáveis de ambiente; não em arquivos publicados.

18

E-mail, Brevo e papel do Firebase

Serviços externos complementam a API, mas não são o armazenamento principal atual.

Brevo pela API HTTP

O serviço de e-mail usa fetch para chamar a API HTTP do Brevo em verificação de e-mail e recuperação de senha. O README registra que o plano gratuito do Render bloqueia SMTP; por isso a integração não depende de porta SMTP.

Tokens de uso único

Links de verificação/redefinição usam tokens aleatórios. O banco guarda hash do token, tipo e expiração; o token é consumido uma vez e documentos vencidos podem ser removidos por TTL.

Firebase legado

O backend pode conferir credenciais de contas antigas pelo Firebase Authentication REST e migrar a conta para MongoDB com hash bcrypt. É um fluxo de transição condicionado às variáveis FIREBASE_*.

Firebase Hosting

Linguagens e como funcionam

O que cada linguagem do projeto é, quem a executa e em que momento.

Uma linguagem é só texto até que algum programa a execute. Esse programa pode ser o navegador, o Node.js ou o Pyodide. Para entender o projeto, pergunte sempre: quem lê este arquivo e o que faz com ele?

Compilada × interpretada

Em uma linguagem compilada (C, Rust), um compilador traduz o programa inteiro em código de máquina antes de rodar. Em uma interpretada (Python), um interpretador lê e executa o texto durante a execução. JavaScript fica no meio: o motor V8 interpreta primeiro e, nos trechos executados muitas vezes, gera código de máquina otimizado na hora (JIT, just-in-time). Por isso você não “compila” o JavaScript do projeto.

Tipagem dinâmica

Em JavaScript e Python o tipo pertence ao valor, não à variável. let x = 5; x = "cinco"; é válido. A vantagem é rapidez para escrever; o custo é que erros de tipo só aparecem quando o código roda. É por isso que o back-end valida tudo o que chega (utils/validacao.js) em vez de confiar no tipo.

O que o navegador faz com uma página

1 · Baixa o HTMLRequisição GET ao servidor estático (Firebase Hosting).
2 · Monta o DOMO parser transforma as tags em uma árvore de objetos. O CSS vira regras de estilo.
3 · Executa o JS<script type="module"> carrega main.js, que importa o resto.
4 · Reage a eventosCliques e respostas de rede disparam funções que alteram o DOM.

Python no navegador: duas linguagens empilhadas

O interpretador do Python (escrito em C) foi compilado para WebAssembly. O navegador roda esse binário e, por cima dele, o texto Python do jogador. O JavaScript apenas envia o texto ao Worker e recebe o resultado — por isso o código do aluno nunca chega ao servidor Node.

Frase útil para a banca: “O mesmo JavaScript roda em dois lugares: no navegador, que tem DOM e fetch mas não acessa o banco; e no Node, que tem sistema de arquivos e rede mas não tem DOM. A linguagem é a mesma; o ambiente é diferente.”

JavaScript do zero, com o código do projeto

Cada conceito vem com a explicação e o lugar onde ele aparece no Escape.py.

1 · Variáveis, tipos e valores

const cria uma referência que não pode ser reatribuída; let permite reatribuir. Use const por padrão. Os tipos primitivos são string, number, boolean, null, undefined e bigint; todo o resto (objetos, arrays, funções) é objeto.

Exemplo didático

const nada = null;              // ausência intencional

2 · Funções e arrow functions

Uma função agrupa instruções reutilizáveis. A arrow function (a) => expressão é uma forma curta; sem chaves, o valor da expressão já é o retorno.

Padrão real · js/nucleo/Api.js
static get(caminho) { return Api.requisitar("GET", caminho); }

corpo = {} é um parâmetro padrão: se ninguém passar o segundo argumento, vale {}. Os métodos get/post/put/patch/excluir são atalhos que chamam um único método requisitar.

3 · Objetos, arrays e desestruturação

Objeto guarda pares chave/valor; array guarda lista ordenada. Desestruturar é extrair campos em variáveis com uma linha.

Padrão real · js/servicos/ServicoPartida.js
const { now } = await Api.get("/time");          // pega só o campo "now"

const arr = (await Api.get("/groups")).map((d) => Grupo.deDados(d));

.map cria um novo array aplicando uma função a cada item. Também são comuns .filter (mantém os que passam no teste), .find (primeiro que passa) e .some (algum passa?).

4 · Template strings, ?. e ??

Padrão real · Api.js e TempoReal.js

cabecalhos.Authorization = `Bearer ${Api.token}`;

O ?. (encadeamento opcional) devolve undefined em vez de lançar erro quando o lado esquerdo é null/undefined. O ?? faz o mesmo papel de “valor padrão”, mas só para null/undefined (o || também troca 0 e "").

5 · Classes, campos privados e static

Uma classe define um molde de objetos com dados e métodos. static pertence à classe, não à instância. O prefixo # torna o membro privado: só o código dentro da classe acessa.

Padrão real · js/nucleo/TempoReal.js

  static ESPERA_MAXIMA_MS = 30000;      // constante da classe
  constructor() {
    this.assinantes = new Map();        // canal → conjunto de funções

  async #abrir() { /* só a própria classe chama */ }

Map é um dicionário com qualquer tipo de chave; Set é uma coleção sem repetição. Aqui, cada canal guarda um Set de funções a chamar quando o servidor avisa uma mudança.

6 · Closures (funções que lembram do contexto)

Uma função interna continua enxergando as variáveis da função externa mesmo depois que esta terminou. É o mecanismo por trás do observar.

Trecho real · TempoReal.observar
observar(canais, carregar, aoAtualizar, aoFalhar = () => {}) {
  let ativo = true;
  let versao = 0;
  const atualizar = async () => {
    const minha = ++versao;
    const dados = await carregar();
    if (ativo && minha === versao) aoAtualizar(dados);
  };
  /* ... assina os canais e chama atualizar() ... */
  return () => { ativo = false; /* cancela */ };
}

Leitura passo a passo: cada chamada de observar cria suas próprias ativo e versao, que atualizar “carrega consigo”. Se duas respostas chegarem fora de ordem, só vale a que tem o maior número (minha === versao) — as antigas são descartadas. A função retornada serve para parar de observar ao sair da tela.

7 · Assíncrono: callbacks, Promises e async/await

JavaScript tem uma única thread: faz uma coisa por vez. Operações lentas (rede, timers) não bloqueiam; elas são entregues ao ambiente e, quando terminam, o resultado volta numa fila. O event loop pega o próximo item da fila quando a pilha de execução está livre.

1 · Chama fetchO código pede a requisição e continua.
2 · Navegador trabalhaA rede roda fora da sua thread.
3 · FilaA resposta entra numa fila de tarefas.
4 · Event loopQuando livre, retoma seu await.
Trecho real · Api.requisitar
let resposta;
try {
  resposta = await fetch(Api.url(caminho), { method: metodo, headers: cabecalhos, body });
} catch {
  throw new ErroApi(0, "SEM_CONEXAO", "Sem conexão com o servidor...");
}
if (resposta.status === 204) return null;
const dados = await resposta.json().catch(() => null);
if (resposta.ok) return dados;

Uma Promise é um objeto que representa um resultado que ainda não chegou (pendente → cumprida ou rejeitada). await pausa aquela função até a Promise resolver, sem travar a página. fetch só rejeita em falha de rede; um 404 ou 500 não rejeita — por isso o código confere resposta.ok. O status 204 significa “sucesso sem corpo”, então não há JSON para ler.

O DOM é a árvore de objetos que representa a página. Você seleciona um elemento, muda seu conteúdo e registra um ouvinte para eventos.

Cada arquivo tem escopo próprio. O que não for export fica invisível para os outros. import { Api } from "./Api.js" traz a classe. import() como função (importação dinâmica) carrega o arquivo sob demanda — é o que main.js faz para cada página.

Um Worker é outra thread, sem acesso ao DOM. Thread principal e Worker só conversam por mensagens (postMessage / evento message), com cópia dos dados. Back-end do zero, com o código do projeto

O que é um servidor, o que acontece em cada requisição e por que o servidor decide, não o navegador.

1 · O que é um back-end

É um programa que fica ligado esperando requisições e devolve respostas. Ele existe porque o navegador do usuário não é confiável: qualquer pessoa pode abrir o console e alterar o JavaScript. Tudo que precisa ser verdadeiro para todos (quem é o dono do grupo, quanto tempo resta, qual enigma foi resolvido) precisa ser decidido num lugar que o usuário não controla.

4 · Middleware: a esteira de processamento

Cada requisição passa por uma fila de funções, na ordem em que foram registradas. Cada uma pode responder e encerrar, ou chamar next() para passar à próxima.

Ordem real · backend/src/app.js

limitadores.geral               4. limite de requisições em /api
/api/auth, /users, /groups,

rotaNaoEncontrada               6. 404 se nada respondeu
tratarErros                     7. converte qualquer erro em JSON

O último é especial: um middleware com quatro parâmetros (erro, req, res, next) é reconhecido pelo Express como tratador de erros. Em middleware/erros.js, erros esperados (ErroHttp) viram a resposta com seu status; qualquer outro é registrado e responde 500 sem expor detalhes internos.

6 · Autenticação passo a passo

Trecho real · middleware/autenticacao.js
const [esquema, token] = (req.get("authorization") || "").split(" ");
if (esquema !== "Bearer" || !token) throw naoAutenticado(..., "TOKEN_AUSENTE");

const dados = lerSessao(req.ctx, token);               // jwt.verify: assinatura + validade
const usuario = await buscarPorId(req.ctx, dados.sub);  // sub = id do usuário
if (!usuario || (usuario.sessionVersion || 0) !== dados.ver) throw ...TOKEN_INVALIDO;
req.usuario = usuario;                                 // as próximas funções usam isto
next();

O JWT carrega só o id (sub) e a versão da sessão (ver), mais emissor, público e expiração. Papel (role), e-mail verificado e perfil são lidos do banco a cada requisição; assim, mudar a senha (que incrementa sessionVersion) derruba tokens antigos imediatamente, o que um JWT sozinho não permitiria.

7 · Banco de dados: o filtro como trava de concorrência

Dois jogadores podem clicar “resolver” ao mesmo tempo. Em vez de ler, comparar em JavaScript e gravar (o que permite corrida), o serviço faz uma única operação condicional no MongoDB:

Trecho real · services/partidas.js, registrarEnigma
const filtro = {
  _id: gid, status: "PLAYING", expiresAt: { $gt: new Date() }, players: uid,
  [`solved.${chave}`]: { $exists: false }          // ainda não resolvido
};
enigma.pistas.forEach((o) => { filtro[`found.${o}`] = { $exists: true }; });  // pistas já achadas

const r = await ctx.db.collection("games").updateOne(filtro, { $set });
if (!r.modifiedCount) throw conflito("Este enigma ainda não pode ser resolvido.", ...);

Leitura: “atualize a partida somente se ela estiver em andamento, dentro do prazo, o usuário for jogador, o enigma ainda não estiver resolvido e as pistas exigidas existirem”. O MongoDB aplica isso de forma atômica num único documento: se dois pedidos chegarem juntos, só um modifica (modifiedCount = 1); o outro recebe 0 e o serviço responde 409. Prazo, participação e pré-requisitos são verificados na mesma operação que grava.

8 · Variáveis de ambiente e configuração

Segredos (JWT_SECRET, MONGODB_URI) não ficam no código: são lidos de process.env em config/ambiente.js. Isso permite usar valores diferentes em desenvolvimento, testes e produção sem alterar arquivos, e impede que o segredo vá para o repositório.

Banco, configuração, e-mail e SSE não são importados diretamente pelos services; chegam num objeto ctx que o criarApp(ctx) injeta em req.ctx. Nos testes, o ctx usa um MongoDB em memória e um e-mail falso — mesmo código, dependências trocadas.

Perguntas possíveis da banca

Toque/click para abrir. Respostas curtas para treinar; desenvolvam com exemplos do próprio código.

Arquitetura e tecnologias

Como a aplicação está organizada?

O navegador entrega a interface HTML/CSS/JavaScript. Ele conversa por HTTP/JSON com uma API Node.js/Express. A API aplica regras e usa o driver oficial para acessar MongoDB Atlas. SSE avisa clientes conectados sobre mudanças, e então o front busca os dados atualizados.

Por que usar JavaScript no front e Node.js no back?

JavaScript já executa nativamente no navegador e também pode rodar no servidor pelo Node. Isso permite usar uma linguagem comum nas duas camadas, embora browser e servidor tenham responsabilidades e ambientes diferentes.

O que significa REST e por que a API usa JSON?

REST organiza operações em recursos e métodos HTTP padronizados. JSON é um formato compacto e amplamente suportado para representar os dados que o front envia e recebe.

Por que separar rotas, controllers e services?

Rotas mapeiam URLs; controllers traduzem requisições/respostas HTTP; services contêm regras de negócio e persistência. A separação facilita leitura, manutenção e testes.

Por que MongoDB em vez de armazenar tudo no navegador?

Os dados precisam ser compartilhados entre integrantes e sobreviver a sessões diferentes. A base central no servidor permite persistência, índices e checagem das regras. O navegador não recebe as credenciais do banco.

Por que usar SSE e não atualizar a tela apenas com polling?

SSE mantém um fluxo HTTP aberto para o servidor enviar avisos com pouca demora, evitando consultas repetidas sem necessidade. Após o aviso, o front faz uma consulta REST para obter a versão atual. O trade-off é conexão aberta e arquitetura atual em memória/instância única.

Qual a diferença entre SSE e WebSocket?

SSE é unidirecional, servidor para cliente, adequado a avisos. WebSocket é bidirecional e atende conversas contínuas nos dois sentidos. Neste projeto, ações do usuário seguem por REST e atualizações chegam por SSE.

Front-end e código do jogo

O que são HTML, CSS e JavaScript e qual função cada um tem?

HTML estrutura e dá significado ao conteúdo; CSS define apresentação e responsividade; JavaScript controla interações, estado de tela, chamadas HTTP e comportamento do jogo.

Como uma página escolhe qual código JavaScript carregar?

O HTML informa data-pagina no body. main.js consulta esse valor em um mapa e importa dinamicamente a classe da página correta, como PaginaSala.

O que é um ES Module e que benefício traz?

É um arquivo que pode importar e exportar funcionalidades com import/export. Permite dividir responsabilidades e declarar dependências em vez de colocar tudo num script global.

Como as imagens da sala viram áreas interativas?

Uma imagem/render ocupa o palco e uma camada SVG posiciona hotspots sobre objetos. Cada hotspot aponta para um objeto com regras de interação; coordenadas normalizadas ajudam a manter posição proporcional ao tamanho da cena.

Como o sistema de dificuldade altera a partida?

A configuração associa dificuldade ao número de enigmas e duração: fácil 3/25 min, médio 4/45 min, difícil 5/60 min. O gerador usa semente para selecionar conteúdo e o servidor define o relógio real da partida.

Como o jogador escreve Python sem instalar Python?

Pyodide executa Python no browser por WebAssembly. O projeto inicia o interpretador em um Web Worker e envia o código para execução/testes, devolvendo o resultado à interface.

Por que executar o código em um Worker?

Um Worker separa a execução da thread principal de UI; assim, o código não bloqueia diretamente a interação. O projeto aplica um limite de tempo e encerra o Worker se a execução travar.

O que são as pistas, enigmas e dependências?

Pistas revelam partes necessárias para resolver enigmas. Configuração e estado da partida guardam quais objetos foram descobertos e quais enigmas foram resolvidos; certas pistas/enigmas ficam bloqueados até as condições anteriores acontecerem. O desafio final exige os demais.

Back-end, segurança e validação

Como uma senha é armazenada?

Ela é processada com bcrypt e o banco armazena o hash, não o texto original. Durante login, bcrypt compara a senha informada com o hash salvo. O custo 12 aumenta o custo computacional do ataque por tentativa.

O que um JWT faz e o que ele não faz?

É uma credencial assinada que comprova emissão pelo servidor e contém claims como assunto/expiração. Ele não é automaticamente criptografado; quem o recebe pode ler claims. A API verifica assinatura/expiração e busca o usuário para autorizar.

CORS impede que alguém não autorizado use a API?

Não. CORS orienta o navegador sobre quais origens podem ler respostas cross-origin. A autenticação e autorização são controles separados e continuam necessárias; scripts de servidor e outros clientes não são protegidos por CORS.

Por que a API precisa validar se o usuário é dono ou membro?

Um identificador na URL não prova permissão. O back-end checa identidade, papel, associação ao grupo, estado da partida, prazo e pré-requisitos para cada ação. A interface não é uma fronteira confiável.

A API executa o Python escrito pelo jogador?

Não no fluxo atual: o Pyodide executa no browser. A API registra progressão e valida regras do domínio, mas o código executável e os testes rodam pelo Worker no cliente. Expliquem essa distinção e a limitação de confiar no resultado enviado pelo cliente.

Como a equipe testa sem usar o banco de produção?

Os testes iniciam MongoDB temporário com mongodb-memory-server e levantam a API real em uma porta local. Serviços externos, como e-mail, podem ser substituídos por dublês.

Qual a diferença entre autenticação e autorização?

Autenticação confirma a identidade; autorização aplica permissões. Um JWT válido pode identificar um usuário, mas a rota ainda verifica se ele é dono, membro, jogador ou administrador.

Por que o timer do jogo é confiável se cada computador tem relógio diferente?

O servidor grava início/expiração e verifica o prazo nas operações. O front consulta hora do servidor e ajusta o cronômetro exibido. Alterar o relógio local não muda a data limite autoritativa armazenada no banco.

Técnicas: “onde isso acontece no código?”

Onde o front-end faz as requisições à API?

Em um único ponto: Api.requisitar, em js/nucleo/Api.js, que chama fetch. Os arquivos de js/servicos/ (ServicoPartida, ServicoGrupos…) não usam fetch diretamente; eles chamam Api.get/post/patch/put/excluir com o caminho. A exceção é a conexão SSE, aberta com fetch em TempoReal.js.

Onde está o endereço do servidor? Como o front sabe se está local ou em produção?

Em js/config.js: se location.hostname for localhost ou 127.0.0.1, usa http://localhost:3000/api; senão usa a API publicada no Render.

Onde o token do usuário é guardado e como ele chega ao servidor?

Após o login, Api.guardarToken grava no localStorage (chave escape-sessao). A cada chamada, Api.requisitar lê o token e envia o cabeçalho Authorization: Bearer …. O localStorage é acessível por JavaScript da página, então XSS é o risco; o projeto mitiga com expiração e uso de textContent.

Onde o servidor valida o token?

No middleware autenticar (backend/src/middleware/autenticacao.js). Ele separa “Bearer” e o token, chama lerSessao (jwt.verify com HS256, emissor e público) e busca o usuário no banco para comparar a sessionVersion. Em falha, responde 401 TOKEN_INVALIDO.

O que acontece no front quando o token expira?

A API responde 401 com código TOKEN_INVALIDO. Em Api.requisitar, o token é apagado do localStorage e um ErroApi é lançado com a mensagem pronta para o usuário.

O que vai dentro do JWT? Papel de administrador está nele?

Não. O token carrega o id (sub), a versão da sessão (ver), emissor, público e expiração. O papel e o estado do e-mail são lidos do banco em cada requisição. Isso permite revogar sessões ao trocar a senha e impede que uma permissão antiga continue valendo.

Onde a conexão em tempo real é aberta, no cliente e no servidor?

Cliente: TempoReal.#abrir faz fetch em /events e lê o fluxo. Servidor: a rota GET /api/events (routes/sistema.js) passa por autenticar e exigirEmailVerificado e chama tempoReal.abrir (services/tempoReal.js), que envia os cabeçalhos text/event-stream e guarda a resposta aberta em um Map por usuário.

Por que não usaram o EventSource do navegador?

EventSource não permite definir cabeçalhos como Authorization. Como o JWT vai no cabeçalho (e não em cookie nem na URL, onde ficaria exposto em logs), o projeto lê o fluxo com fetch e implementa a reconexão manualmente.

Onde o servidor decide avisar os outros jogadores?

Ao fim de cada operação de services/partidas.js há avisar(ctx, grupo, gid), que chama avisarGrupo e depois ctx.tempoReal.notificar(membros, "partida:{gid}"). No cliente, ServicoPartida.observar está assinado nesse canal e refaz GET /api/games/{gid}.

O que acontece se a conexão SSE cair?

TempoReal tenta reconectar com espera crescente (1 s, 2 s, 4 s… até 30 s). Na reconexão, o servidor manda o canal conectado; como avisos podem ter se perdido, o cliente recarrega os dados de todos os assinantes. Um ping a cada 25 s mantém a conexão viva contra proxies.

Onde o tempo da partida é definido? O que impede o jogador de mexer no relógio?

Em iniciarPartida (services/partidas.js): expiresAt = agora + DIFICULDADES[dificuldade].minutos, gravado no banco. As operações de pista/enigma filtram por expiresAt: { $gt: new Date() } no próprio updateOne. O front só exibe: ServicoPartida.deslocamentoMs consulta GET /api/time e compensa a diferença entre o relógio local e o do servidor.

Dois jogadores resolvem o mesmo enigma ao mesmo tempo. O que acontece?

O updateOne em registrarEnigma só altera se solved.{chave} ainda não existir. O MongoDB aplica a condição de forma atômica no documento: um pedido modifica, o outro recebe modifiedCount = 0, e o service responde 409 ENIGMA_JA_RESOLVIDO. Não há condição de corrida entre “ler” e “gravar” porque são uma operação só.

Como o servidor garante que o enigma final só conclui depois dos demais?

Em registrarEnigma, se o enigma tem final, o filtro acrescenta solved.{k}: { $exists: true } para todos os outros enigmas da ordem. Se algum faltar, nada é modificado e a resposta é 409 ENIGMA_BLOQUEADO. Se passar, o mesmo $set grava status: "COMPLETED", a data de término e a pontuação.

O cliente pode mandar uma pontuação falsa? Como o servidor reage?

Pode tentar. O servidor valida formato e faixa (inteiro(corpo.score, …, 0, 5000), dicas de 0 a 3), mas não recalcula a pontuação a partir do código Python, porque quem executa o teste é o navegador. Essa é uma limitação conhecida e deve ser dita abertamente: a integridade do fluxo é do servidor; a do resultado do teste é do cliente.

Onde os erros viram resposta HTTP?

Os services lançam erros tipados (naoAutenticado, proibido, conflito… de utils/erros.js). O Express 5 encaminha qualquer rejeição de handler async para tratarErros (middleware/erros.js), que monta { erro: { codigo, mensagem } } com o status certo. Erros inesperados viram 500 sem expor detalhes. No front, Api.requisitar converte o JSON em ErroApi.

Onde ficam o CORS e o limite de requisições?

Ambos em backend/src/app.js: cors({ origin … }) compara a origem com ctx.config.origens, e app.use("/api", limitadores.geral) aplica o limite geral. Limites mais rígidos para rotas sensíveis são passados a rotasAutenticacao(limitadores) (definidos em middleware/limites.js).

Por que há trust proxy no app.js?

No Render a API fica atrás de um proxy. Sem essa opção, todos os pedidos pareceriam vir do mesmo IP (o do proxy) e o limitador de taxa trataria todos os usuários como um só. Com trust proxy: 1, o Express lê o IP real do cabeçalho X-Forwarded-For.

Qual é a rota usada para verificar se o servidor está saudável? Por que ela consulta o banco?

GET /api/health (sistemaController.saude) faz db.command({ ping: 1 }) e responde 200 ou 503. O Render usa essa rota como health check; consultar o banco evita marcar como saudável uma API que está no ar mas sem conexão com o MongoDB.

Onde a senha é transformada em hash? O que é o “hash fictício” do login?

Em services/autenticacao.js, com bcrypt.hash(senha, CUSTO_BCRYPT). No login, quando o e-mail não existe, o código ainda executa bcrypt.compare contra um hash fictício para que o tempo de resposta seja parecido com o de uma conta real; isso dificulta descobrir quais e-mails têm cadastro por diferença de tempo.

Onde são criados os índices do MongoDB e para que servem?

Em backend/src/config/banco.js, na inicialização. Exemplos: users.email único (impede duplicidade), groups.members (acelera “meus grupos”), messages { groupId, createdAt } (histórico do chat ordenado) e índices TTL em authTokens.expiresAt e messages.expiresAt, que removem documentos vencidos automaticamente.

Como uma página sabe qual classe iniciar e onde isso é feito?

Em js/main.js: lê document.body.dataset.pagina, busca a classe em Aplicacao.PAGINAS, faz import(`./paginas/${classe}.js`) e chama new modulo[classe]().iniciar().

Onde o código Python do jogador é executado e como o travamento é tratado?

ExecutorPython.executar envia uma mensagem ao PyodideWorker.js. Um setTimeout de TEMPO_MAXIMO_MS = 6000 roda na thread principal: se estourar, o Worker é terminado (terminate()) e descartado, e o resultado é tempo_esgotado. A próxima execução cria um Worker novo.

Como o front evita mostrar dados antigos quando duas respostas chegam fora de ordem?

Em TempoReal.observar, cada carregamento incrementa um contador versao; ao terminar, só aplica o resultado se minha === versao. Respostas mais velhas que chegam depois são ignoradas.

Como os testes sobem a API sem usar o banco real?

criarApp(ctx) recebe as dependências por parâmetro. Os testes constroem um ctx com mongodb-memory-server e e-mail falso, sobem o app numa porta local e fazem requisições HTTP reais. O código dos services é o mesmo de produção.

Por que o servidor estático e a API ficam em domínios diferentes e o que isso muda?

O front é servido como arquivos estáticos e a API roda no Render. Como são origens diferentes, o navegador exige CORS na API e impede o uso simples de cookies de sessão entre as duas; por isso a sessão é um token enviado em cabeçalho. É também a razão do JWT estar no localStorage.
