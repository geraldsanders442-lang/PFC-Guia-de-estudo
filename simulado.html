Arquitetura

prioridade alta

Expliquem a arquitetura do Escape.py de ponta a ponta.

O que o professor quer descobrir: Se vocês têm uma visão do sistema inteiro e sabem separar responsabilidades.

Nível 1 · Resposta oral

É uma aplicação cliente-servidor. O front é estático, em HTML, CSS e módulos JavaScript. Ele chama uma API própria em Node.js com Express, e só ela acessa o MongoDB Atlas. Quando algo muda, a API avisa por Server-Sent Events e o front busca os dados de novo. O Python do jogador roda no navegador com Pyodide, dentro de um Web Worker.

Nível 2 · Entendendo a resposta

Três lugares executam código: navegador (tela e regras de apresentação), Worker (Python) e servidor (autorização, regras e persistência). A divisão segue um princípio: o que precisa ser verdade para todos fica no servidor. A exceção honesta é a correção do Python, que fica no cliente. Ver diagrama.

A rota liga método e caminho a uma fila de funções. Os middlewares verificam coisas comuns, como token e e-mail. O controller lê a requisição e escolhe o status da resposta. O service aplica a regra e fala com o banco.

JavaScript

prioridade alta

Expliquem async, await e Promise usando uma função do projeto.

O que o professor quer descobrir: Domínio real do JavaScript assíncrono.

Nível 1 · Resposta oral

Em Api.requisitar, fetch devolve uma Promise, um resultado que ainda vai chegar. O await pausa só aquela função; a página continua respondendo. Quando a resposta chega, a função continua e usamos try/catch para falha de rede.

Nível 2 · Entendendo a resposta

O JavaScript tem uma thread principal e um event loop. A rede é feita pelo navegador; ao terminar, a continuação entra na fila. Detalhe importante: fetch não rejeita em 404 ou 500, por isso testamos resposta.ok. Há um segundo await em resposta.json().

Conferimos o tipo antes de consultar. Se alguém mandar um objeto como {"$ne": null} no lugar do e-mail, a função texto rejeita com 400. As chaves que viram caminho de campo seguem uma expressão regular.
